# بررسی پرامپت و اصلاحات عملکرد

تاریخ: ۲۰۲۶-۱۰-۳۰. مرجع گزارش درخواستی:
`https://gtmetrix.com/reports/185.93.88.81/sOjGZUad/`.

## محدودیت شواهد

پراکسی محیط درخواست GTmetrix را در CONNECT با ۴۰۳ و درخواست IP سایت را با ۴۰۳
رد کرد. بنابراین محتوای این گزارش، Waterfall، Top Issues، Browser Timings،
مکان/نسخهٔ مرورگر گزارش و اعداد آن در این بررسی مشاهده نشده‌اند.
هیچ تحلیل خط‌به‌خط یا عدد قبل/بعد GTmetrix ادعا نمی‌شود.
آزمایش‌های زیر روی checkout و کاتالوگ نمونهٔ محلی‌اند.

## اشکال‌های پرامپت اولیه

- مقیاس معمول Grade در GTmetrix از A تا F است؛ «A+» معیار پذیرش مستقلی نیست.
  هدف دقیق را Grade A و Performance/Structure حداقل ۹۷ بنویسید؛ حداقل ۹۰ را
  جداگانه به‌عنوان حد پذیرش اضطراری تعریف کنید.
- امتیاز عملکرد، Structure، امتیاز SEO داخلی، رتبهٔ گوگل و AI readiness معیارهای
  متفاوت‌اند؛ افزایش یکی اثبات افزایش دیگری نیست.
- حفظ ۸+۸ و استوری لازم است، اما کلیک اول، صفحه‌کلید، کاربر دارای سبد/نشست،
  بارگذاری سرد، cache hit و شکست/کندی resource هم باید آزمون شوند.
- نسخهٔ دستی critical CSS می‌تواند با قالب فاصله بگیرد. `media=print` به‌تنهایی
  تضمین FCP/CLS خوب نیست؛ باید هندسهٔ صفحه بدون باندل نهایی نیز درست باشد.
- کش مهمان بدون احترام به Set-Cookie، private/no-store و مسیرهای خصوصی خطرناک است.
  نباید برای بالا بردن Structure یا کاهش TTFB هدرهای محافظ را نادیده گرفت.
- `immutable` برای URL تصویری که درجا بازنویسی می‌شود مناسب نیست؛ versioning یا
  filename جدید لازم است. حفظ تصاویر در deploy به‌تنهایی cache invalidation نیست.
- نام فایل `01-lcp.webp` به معنی LCP واقعی نیست؛ عنصر LCP باید از trace همان تست
  تعیین شود. preload باید دقیقاً با URL تصویر نمایش‌داده‌شده یکسان باشد.
- حدس «سقف فیزیکی Seattle→Iran» کافی نیست؛ TTFB، RTT، حجم/فشرده‌سازی، زمان decode،
  render delay، رقابت font/CSS/image و سرد/گرم بودن cache باید جدا اندازه‌گیری شوند.
- حداقل ۳ اجرای همسان و میانه/دامنهٔ نتایج، از یک اجرای خوش‌شانس معتبرتر است.
- `curl -w` بدون fail/status assertion تست سلامت نیست. optimizer شکست‌خورده،
  `git pull || true` و نبود rollback نباید deploy موفق گزارش شوند.
- llms.txt/ai.txt و JSON-LD تضمین citation یا نمرهٔ AI نیستند؛ دادهٔ صحیح و همخوان با
  محتوای قابل مشاهده لازم است. نظر، rating، ادعای تجربهٔ خرید یا SERP ساختگی ممنوع است.

## اصلاحات آماده‌شده و شواهد محلی

| رفتار | پیش از تغییر | پس از تغییر |
| --- | --- | --- |
| کلیک اول منو/سبد/ورود با ۲۵۰ms تأخیر site.js | هر سه بی‌اثر | هر سه باز می‌شوند |
| استوری | باز می‌شد | باز می‌شود |
| تعداد محصولات خانه | ۸ ویژه + ۸ برتر | همان ۸+۸ |
| تعداد استوری DB نمونه | ۱۲ | ۱۲ |
| CLS موبایل در تأخیر مصنوعی ۱۵۰۰ms باندل CSS | حدود ۰٫۰۹۴۲ | حدود ۰٫۰۰۳۱ |
| هندسهٔ header/story/hero پیش و پس از CSS | جابه‌جایی محسوس | در تست همسان، بدون اختلاف معنادار |
| تست‌های .NET | ۳۴ تست موجود | ۵۵ تست با regressionهای کش و تصاویر |
| nginx | نادیده‌گرفتن هدرهای محافظ و کش عمومی مسیرها | تست HIT عمومی و bypass خصوصی موفق |

این CLS نمونهٔ کوتاه آزمایشگاهی با Chromium محلی است؛ نه نتیجهٔ GTmetrix، نه
CrUX و نه تضمین رفتار همهٔ دستگاه‌ها. LCP/FCP/TBT/Speed Index زنده اندازه‌گیری نشده‌اند.

تغییرات کد:

- JS حساب قبل از site.js بار می‌شود؛ کلیکِ پیش از آماده‌شدن handlerها پس از load
  بازپخش می‌شود. انتظار ثابت ۶ ثانیه‌ای با scheduling idle/interaction جایگزین شده است.
- CSS بحرانی از همان باندل و media queryهای قالب ساخته می‌شود؛ font preload با URL
  واقعی CSS یکسان است و استایل کامل همچنان async با noscript fallback باقی می‌ماند.
- تولید CSS بحرانی حجم inline بیشتری دارد: HTML ذخیره‌شدهٔ نمونه با gzip سطح ۱
  حدود ۲۵KB بود و نمونهٔ پس از تغییر حدود ۳۸KB شد. این هزینهٔ واقعی حذف اختلاف
  قالب اولیه است و باید در Waterfall زنده در برابر بهبود render delay سنجیده شود.
- منطق تکراری هدرهای عمومی از Program حذف شد. session/cart، خطا، پاسخ خصوصی و
  Set-Cookie از public cache خارج‌اند. برنامه برای پاسخ‌های غیرعمومی no-store می‌گذارد.
- nginx هدرهای محافظ origin را رعایت می‌کند؛ مسیرهای عمومی whitelist دارند،
  `_mv` مانع cache hit نیست و session/cart آن را bypass می‌کنند.
- asset versionدار immutable است؛ فایل بدون version فقط یک ساعت cache می‌شود.

تست nginx روی binary نسخهٔ ۱٫۲۶٫۳ با metadata امضاشدهٔ Debian و checksum تأییدشده،
upstream آزمایشی و پورت موقت اجرا شد؛ nginx سیستم یا VPS تغییر نکرد.
اسکریپت‌ها: `verify-home-performance.cjs`، `verify-proxy-cache.py` و `PublicCacheSafetyTests.cs`.

اصلاحات تکمیلی مسیر انتشار و LCP:

- تصاویر کم‌حجم محصول نیز نسخهٔ LCP می‌گیرند؛ تصویر WebP انتخاب‌شده برای نمایش بر
  فایل اصلی هم‌نام اولویت دارد. منبع اصلی حفظ و LCP منقضی با تغییر منبع بازتولید می‌شود.
- مشتق‌های `-lcp` دوباره به `-lcp-lcp` تبدیل نمی‌شوند. خطای optimizer، CLI را با status ۱
  تمام می‌کند؛ این رفتار علاوه بر unit test، با اجرای واقعی CLI در پوشهٔ مجزا بررسی شد.
- انتشار با lock، checkout تمیز، build در staging، validation nginx، maintenance عمومی،
  توقف کامل برنامه، backup از SQLite با API سازگار با WAL و حفظ config/App_Data/images انجام می‌شود.
- قبل از بازکردن ترافیک، Kestrel و nginx با ۸+۸ محصول، استوری و همان LCP واقعی بررسی می‌شوند.
  manifest نسخه `RELEASE_COMMIT` داخل publish ذخیره می‌شود.
- شکست pull/build/nginx/optimizer/start/smoke باعث گزارش خطا و بازگشت نسخه/config می‌شود؛
  اگر recovery نیز شکست بخورد، maintenance باقی می‌ماند. marker متعلق به عملیات دیگر حذف نمی‌شود.
- ۶ تست Python شامل سناریوهای خطا، حفظ سفارش نمونه و آپلود/config، rollback و کنترل
  سلامت HTTP اجرا و موفق شدند. تست‌های فرمان‌های VPS از fixture استفاده کردند؛
  این نتیجه اثبات deploy واقعی نیست. محدودیت دورهٔ maintenance و config واقعی سرور هنوز باز است.

## پرامپت پیشنهادی برای ادامهٔ کار

```text
روی Movasseghi Store، ASP.NET Core 10 + Razor + SQLite + nginx + Kestrel کار کن.
هدف: حفظ رفتار و دادهٔ production، Grade A در GTmetrix، هدف Performance و Structure
هر دو >=97. رسیدن به نمره را تضمین نکن و میان نتیجهٔ محلی و production تفکیک روشن بگذار.
مخزن و .cursor/rules/seo-score-integrity.mdc و docs/PROJECT-MAP.fa.md را ابتدا بخوان.

Production موقت: http://185.93.88.81/، PathBase خالی؛
VPS: /MOVASSEGHISTORE/src و /MOVASSEGHISTORE/publish؛ Kestrel روی 5080 و nginx روی 80.
بدون انتشار و مشاهدهٔ نتیجه روی سرور، عبارت «رفع‌شده در production» را به کار نبر.

۱. گزارش sOjGZUad را واقعاً باز کن. تاریخ، test location، viewport، نسخه Chrome/Lighthouse،
   حالت اتصال و cache را ثبت کن. تمام auditهای failed و فرصت‌ها را به resource/خط کد وصل کن.
   LCP element و سهم TTFB/load delay/load duration/render delay را از trace استخراج کن.
   اگر دسترسی مسدود بود، مشخص کن دقیقاً چه مدرکی خوانده نشده؛ عدد و تشخیص نساز.

۲. قبل از تغییر baseline بگیر: مرورگر موبایل و دسکتاپ، ۸+۸ محصول، استوری بالای هیرو و
   بازشدن modal با کلیک اول، هیرو و CSS از فریم‌های اول، ورود/سبد/منو با لمس و صفحه‌کلید.
   cold/warm cache، کوکی _mv، session، سبد غیرخالی و کاربر واردشده را جدا تست کن.

۳. اصلاح را با ریشهٔ اندازه‌گیری‌شده انجام بده. محتوای SSR و SEO را حفظ کن.
   CSS بحرانی از قواعد واقعی قالب، async stylesheet بدون timeout نمایشی، فونت self-hosted،
   preload منطبق با تصویر LCP واقعی، fetchpriority بالا فقط برای تصویر لازم، و lazy loading
   برای تصاویر خارج viewport. style/layout/long task و رقابت شبکه را اندازه بگیر.
   JS ضروری باید تعامل اول را حفظ کند؛ پنهان‌کردن کار تا بعد از پنجرهٔ benchmark مجاز نیست.
   برای bot یا GTmetrix محتوای سبک‌تر و متفاوت از کاربر واقعی نساز.

۴. در همهٔ لایه‌های کش، Set-Cookie، Authorization، هویت، session، cart، query و Vary را
   بررسی کن. Order/Invoice/Payment/Cart/Account/Admin/API را وارد کش عمومی نکن.
   no-store/private را override نکن. آمار و antiforgery را به خاطر cache خراب نکن.
   cache invalidation قیمت/محتوا و asset versioning را تست کن؛ تصویر بازنویسی‌شونده immutable نیست.

۵. build و پروژهٔ تست واقعی را اجرا کن؛ solution فعلی تست‌ها را شامل نمی‌شود.
   مرورگر با تأخیر CSS و JS، no-JS fallback و شبکهٔ کند را هم تست کند.
   قیمت/واحد تومان و ریال، canonical، sitemap، JSON-LD و محتوای قابل crawl را حفظ کن.
   SEO score یا نظر مشتری ساختگی تولید نکن. llms/ai فایل تضمین رتبه نیستند.

۶. پیش از deploy: commit دقیق، وضعیت تمیز/حفظ تغییرات کاربر، دسترسی SSH، فضای دیسک،
   backup قابل بازیابی از SQLite (با توجه به WAL)، config، App_Data و آپلودها را تأیید کن.
   شکست pull/build/optimizer/health check باید روشن باشد. staging و nginx -t را پیش از
   سوییچ اجرا کن؛ downtime را محدود و rollback خودکار/آزموده داشته باش.
   DB production را با snapshot مخزن جایگزین نکن؛ هیچ secret یا فایل موقت commit نشود.

۷. فقط commit آزموده‌شده را به main بفرست و روی VPS همان SHA را منتشر کن.
   SHA سورس و release روی سرور، سلامت Kestrel و nginx، تصویر LCP انتخاب‌شده، ظاهر و
   تعاملات و حفظ فایل‌های ماندگار را بررسی کن. status غیر۲۰۰ یا PID به‌تنهایی موفقیت نیست.

۸. GTmetrix را با همان تنظیمات از نو اجرا کن و لینک جدید بده؛ در صورت دسترسی حداقل
   سه اجرای همسان و میانه/دامنه را ثبت کن. هدف‌ها: TBT<120ms، CLS<=0.01؛ LCP<1s،
   FCP<0.8s و SI<1.1s اهداف stretch هستند و باید با شواهد همان موقعیت سنجیده شوند.
   اگر شبکه مانع بود، عدد اندازه‌گیری‌شده و سهم backend/network/render را گزارش کن.
   CDN/دامنه/HTTPS را پیشنهاد جدا بده، بدون وعدهٔ قطعی نمره و بدون کش عمومی محتوای خصوصی.

خروجی فارسی: ریشهٔ هر ایراد و شاهد، تغییرات، تست‌های گذرانده/ناموفق/اجرانشده، SHA،
وضعیت دقیق deploy، لینک گزارش جدید و جدول قبل/بعد واقعی. در نبود دسترسی، نیاز مشخص
را اعلام کن؛ ادامهٔ کار مستقل را انجام بده و مرحلهٔ مسدود را موفق گزارش نکن.
```

## کار باز

تحلیل کامل گزارش اصلی، اندازه‌گیری زنده، استقرار و Re-Test جدید هنوز انجام نشده‌اند.
نیازها: فعال‌شدن دسترسی HTTP محیط به GTmetrix/IP، اتصال SSH معتبر و مجاز به VPS،
و امکان اجرای تست GTmetrix با تنظیمات درخواست‌شده. کلید/رمز باید در مسیر امن محیط
فراهم شود، نه متن چت. نیازی به وعدهٔ نمره یا تکرار تست توسط کاربر به جای عامل نیست.
